# 1. Purpose

The Metadata Synchronization Service is a standalone middleware responsible for synchronizing execution metadata generated by the Test Case Management (TCM) platform into MinIO.

The service was designed with one primary objective:

> Automatically synchronize execution metadata into the correct metadata.json file without requiring testers to manually manage metadata.

Rather than embedding MinIO logic inside the Test Case Management platform, synchronization responsibilities are delegated to a dedicated service.

This separation allows both systems to evolve independently while maintaining a well-defined integration contract.

---

# 2. Scope

This playbook serves as the primary technical reference for developers maintaining or integrating with the Metadata Synchronization Service.

It explains:

- the architecture of the synchronization service
- folder hierarchy conventions
- version resolution
- AP Model resolution
- metadata path resolution
- synchronization workflow
- validation rules
- duplicate detection
- overwrite behaviour
- deployment considerations
- integration requirements

This document intentionally explains both **what the service does** and **why it behaves that way**.

Future modifications should preserve the conventions documented here unless accompanied by corresponding changes to both the TCM platform and the Metadata Synchronization Service.

# 3. System Overview

The Metadata Synchronization Service operates between the Test Case Management platform and MinIO.

Its responsibility is to translate execution information generated inside TCM into metadata updates stored within MinIO.

The service is invoked only after an execution has already been successfully persisted inside the TCM database.

This ordering guarantees that synchronization failures never result in lost execution records.

```
                        Tester
                           │
                           │
                    Executes Test
                           │
                           ▼
               Updates Execution Details
                           │
                           ▼
                     Clicks Submit
                           │
                           ▼
          Execution Persisted inside TCM
                           │
                           ▼
        Metadata Synchronization Request
                           │
                           ▼
       Metadata Synchronization Service
                           │
        ┌──────────────────┼──────────────────┐
        │                  │                  │
        ▼                  ▼                  ▼
 Resolve Version     Resolve Metadata     Validate Request
                           │
                           ▼
                 Detect Duplicate Metadata
                           │
                           ▼
                    Merge Metadata
                           │
                           ▼
                 Upload metadata.json
                           │
                           ▼
              Synchronization Response
                           │
                           ▼
                           TCM
```

The synchronization service acts as an intermediary responsible for translating business information into repository updates.

# 5. Component Responsibilities

The system consists of three independent components.

---

## 5.1 Test Case Management (TCM)

Responsibilities:

- Create projects
- Create test runs
- Execute test cases
- Store execution results
- Trigger metadata synchronization
- Display synchronization status

TCM **does not**:

- read metadata.json
- write metadata.json
- access MinIO
- merge metadata
- determine repository paths

Its responsibility ends after submitting the synchronization request.

---

## 5.2 Metadata Synchronization Service

The Metadata Synchronization Service owns the complete synchronization process.

Responsibilities include:

- validating incoming requests
- resolving repository hierarchy
- resolving firmware versions
- deriving AP Models
- locating metadata.json
- validating metadata
- duplicate detection
- metadata merging
- uploading metadata.json
- returning synchronization status

The service contains all repository-specific business logic.

No MinIO-specific logic should exist inside the TCM platform.

---

## 5.3 MinIO

MinIO acts purely as an object storage system.

Its responsibilities are intentionally minimal.

MinIO stores:

- project buckets
- firmware versions
- repository hierarchy
- metadata.json files

MinIO contains **no business logic**.

It should never perform:

- validation
- duplicate detection
- metadata formatting
- synchronization decisions

All such behaviour belongs exclusively to the Metadata Synchronization Service.

---

# 6. Design Philosophy

Several architectural principles guided the implementation of the Metadata Synchronization Service.

---

## 6.1 Separation of Concerns

Each component owns exactly one responsibility.

| Component | Responsibility |
|-----------|----------------|
| TCM | Execution Management |
| Metadata Sync Service | Metadata Synchronization |
| MinIO | Metadata Storage |

Keeping these responsibilities isolated reduces coupling between systems and simplifies future maintenance.

---

## 6.2 Convention Over Configuration

Rather than requiring every project to configure custom repository paths, the service follows predefined conventions.

Examples include:

- Bucket naming
- Root folder naming
- Version folder naming
- AP Model resolution
- Repository hierarchy
- Metadata filename

Projects following these conventions require no project-specific implementation.

---

## 6.3 Project Agnostic Design

The Metadata Synchronization Service contains no project-specific logic.

Instead, all projects integrate using the same conventions.

Whether synchronizing:

- Legacy Ruckus
- Enterprise AP
- H550
- R760

the service executes the same workflow.

Only project data changes.

The synchronization logic remains identical.

---

## 6.4 Non-Blocking Synchronization

Execution persistence is always prioritised over metadata synchronization.

The execution is saved inside TCM before synchronization begins.

Consequently:

- MinIO failures do not lose execution data.
- Metadata synchronization can be retried.
- Repository failures never rollback execution updates.

This behaviour improves reliability while reducing operational risk.

---

# 7. Integration Contract

The Metadata Synchronization Service and the Test Case Management platform communicate through a well-defined integration contract.

The service assumes the TCM platform follows the conventions documented within this playbook.

Examples include:

- Test Run naming
- Folder hierarchy
- Version structure
- Metadata layout
- Payload schema

These conventions form part of the integration contract.

Changing any of these conventions without updating the Metadata Synchronization Service may prevent successful synchronization.

Whenever integration conventions change, both systems must be updated together.

---

# 8. Synchronization Lifecycle

The synchronization process begins only after execution information has already been committed to the database.

```
Tester

    │

Execute Test Case

    │

Submit Execution

    │

Execution Stored in Database

    │

Metadata Sync Request

    │

Resolve Repository Location

    │

Download metadata.json

    │

Validate Metadata

    │

Detect Duplicate Entries

    │

Merge Metadata

    │

Upload Updated metadata.json

    │

Return SUCCESS / FAILED

    │

Display Synchronization Status
```

This workflow ensures execution persistence remains independent from metadata synchronization.

If synchronization fails, execution information remains safely stored inside the Test Case Management platform.


# 9. Bucket Naming Convention

Each TCM project is mapped to exactly one MinIO bucket.

The bucket acts as the root container for every firmware version, AP Model, feature, test run and metadata file belonging to that project.

Example:

| TCM Project | MinIO Bucket |
|-------------|--------------|
| Legacy Ruckus | legacyruckus |
| Enterprise AP | enterpriseap |
| WiFi Controller | wificontroller |

## Bucket Naming Rules

Bucket names should:

- use lowercase characters
- avoid spaces
- avoid special characters
- remain unique across all projects
- remain stable throughout the lifetime of the project

Example

```
✓ legacyruckus

✓ enterpriseap

✓ wifi_controller
```

Avoid

```
✗ Legacy Ruckus

✗ Legacy-Ruckus

✗ Legacy Ruckus Project
```

Changing a bucket name is considered a breaking change because every metadata path begins with the bucket.

---

# 10. Root Repository Structure

Each bucket follows a fixed repository structure.

The first folder inside every bucket must always be

```
Test_Plan
```

Example

```
legacyruckus/

└── Test_Plan/
```

The Metadata Synchronization Service assumes this folder exists.

If the folder cannot be located, synchronization immediately fails.

This convention removes the need to configure project-specific repository roots.

# 11. Firmware Version Resolution

Every project may contain multiple firmware versions.

Example

```
legacyruckus/

└── Test_Plan/

    ├── V71/
    ├── V72/
    ├── V73/
    ├── V74/
    └── V75/
```

The Metadata Synchronization Service resolves the firmware version before any metadata path can be constructed.

Version resolution follows two possible workflows.

---

## 11.1 Automatic Version Resolution

If no firmware version is supplied by the TCM platform, the service automatically discovers the most recent version available within the repository.

Internally, the service:

1. Lists every folder beneath `Test_Plan/`
2. Extracts unique version folders
3. Sorts the versions using a numeric-aware comparison
4. Selects the newest version

For example

```
Test_Plan/

├── V71
├── V72
├── V73
├── V74
└── V75
```

The resolved version becomes

```
V75
```

---

Another example

```
Test_Plan/

├── V7.2
├── V7.9
├── V7.10
└── V8
```

The numeric-aware comparison correctly resolves

```
V8
```

instead of incorrectly treating

```
V7.10
```

as being smaller than

```
V7.9
```

This behaviour is implemented using JavaScript's numeric locale comparison.

---

## 11.2 Explicit Version Override

The synchronization request may optionally specify a firmware version.

Example

```
Version

V73
```

Instead of automatically selecting the newest version, the Metadata Synchronization Service validates that the requested version exists.

If found

```
Test_Plan/

└── V73/
```

is selected.

If the version does not exist, synchronization terminates with an appropriate validation error.

Example

```
Version Requested

V80
```

Repository

```
Test_Plan/

V71
V72
V73
V74
```

Result

```
ERROR

Version "V80" does not exist.
```

---

## Version Resolution Priority

The Metadata Synchronization Service always follows the same priority order.

```
Version supplied?

        │

   Yes ─────► Validate supplied version

        │

        No

        │

Automatically discover latest version
```

This behaviour forms part of the integration contract.

---

# 12. AP Model Resolution

After resolving the firmware version, the Metadata Synchronization Service derives the AP Model from the Test Run name.

Unlike the firmware version, the AP Model is not transmitted as an independent field.

Instead, it is extracted directly from the Test Run name according to a predefined naming convention.

---

## Supported Test Run Naming Conventions

The service supports two formats.

```
<AP_MODEL>
```

or

```
<AP_MODEL>_<DESCRIPTION>
```

Examples

| Test Run Name | Resolved AP Model |
|---------------|-------------------|
| R750 | R750 |
| R750_May4_May8 | R750 |
| R760_Regression | R760 |
| H550_InternalIssues | H550 |
| H550 | H550 |

---

## Resolution Algorithm

Internally, the Metadata Synchronization Service examines the Test Run name.

If an underscore exists

```
_
```

the service extracts everything before the first underscore.

Example

```
R750_May4_May8
```

↓

Resolved AP Model

```
R750
```

---

Example

```
R760_Regression
```

↓

Resolved AP Model

```
R760
```

---

If no underscore exists

```
H550
```

↓

Resolved AP Model

```
H550
```

Only the first underscore is considered during resolution.

Therefore

```
R750_May4_May8
```

still resolves to

```
R750
```

rather than

```
R750_May4
```

This convention is implemented consistently for every synchronization request.

---

## Why AP Model Resolution Exists

The AP Model naming convention eliminates the need for TCM to explicitly send an additional AP Model field.

Instead, a single Test Run name contains sufficient information for the Metadata Synchronization Service to derive the repository hierarchy automatically.

This reduces payload complexity while ensuring consistent repository organization.

---

# 16. Synchronization Request Validation

Every synchronization request first passes through a validation phase before any repository operations are performed.

The purpose of this stage is to ensure that the request contains the minimum information required to locate and update the appropriate metadata file.

This validation is performed by the `acceptSyncRequest()` function.

Unlike business validation, which occurs later during synchronization, request validation only verifies the structure and completeness of the incoming payload.

---

## Validation Flow

```
Incoming Request

        │

Request Exists?

        │

Request is JSON Object?

        │

Required Fields Present?

        │

Validation Passed
```

If any validation step fails, synchronization is immediately rejected without performing any MinIO operations.

---

## Required Fields

The following fields are mandatory for every synchronization request.

| Field | Description |
|--------|-------------|
| project | Project name used to resolve the target bucket |
| testRun | Test Run name used to derive the AP Model |
| feature | Repository feature folder |
| run | Execution run name |
| test_case | Test case identifier |
| status | Execution status |
| executedBy | User performing the execution |
| executedAt | Execution timestamp |

If any required field is absent, the service returns a validation error.

Example

```json
{
    "success": false,
    "message": "feature is required."
}
```

---

## Validation Responsibilities

The request validator intentionally performs only structural validation.

It does **not** verify:

- bucket existence
- firmware version existence
- repository structure
- metadata availability
- duplicate executions

These checks occur later during metadata preparation.

Separating structural validation from business validation simplifies maintenance while producing more meaningful error responses.

---

# 17. Metadata Synchronization Preparation

After the request has been validated, the Metadata Synchronization Service begins preparing the synchronization process.

Preparation is responsible for locating the exact metadata file that will be updated.

This phase performs every repository lookup before any metadata is modified.

The preparation stage is implemented by the `prepareMetadataSynchronization()` function.

---

## Preparation Workflow

```
Resolve Bucket

        │

Resolve Firmware Version

        │

Extract AP Model

        │

Construct Feature Folder

        │

Discover Repository Type

        │

Resolve Run Parent

        │

Discover Run Directory

        │

Construct metadata.json Path

        │

Read Existing Metadata

        │

Duplicate Detection

        │

Build Execution Metadata

        │

Return Prepared Context
```

Only after this preparation completes successfully does the service proceed to the merge and write phase.

---

# 18. Bucket Resolution

Every project stored within the Test Case Management platform maps to exactly one MinIO bucket.

The synchronization service resolves the bucket using the project name supplied within the synchronization request.

Internally this is handled by the Bucket Resolver.

```
Project

↓

Bucket
```

Example

```
Project

Legacy Ruckus
```

↓

```
Bucket

legacyruckus
```

The resolved bucket becomes the root container for every subsequent repository lookup.

If bucket resolution fails, synchronization terminates immediately.

---

## Why Bucket Resolution Exists

Separating bucket resolution from synchronization logic provides several advantages.

- Project names remain independent from storage names.
- Repository naming conventions remain centralized.
- Bucket mappings can evolve without modifying synchronization logic.
- Synchronization remains project agnostic.

# 19. Firmware Version Resolution

After determining the bucket, the synchronization service resolves the firmware version.

Version resolution follows the mechanism described in Part I.

The preparation stage simply invokes the Version Resolver and receives the resolved version.

```
Bucket

↓

Version Resolver

↓

Resolved Version
```

Examples

```
V75
```

or

```
V7.10
```

Depending on the synchronization request, the Version Resolver may either

- automatically determine the latest version, or
- validate an explicitly supplied version override.

The preparation stage does not perform version discovery itself; it delegates this responsibility to the dedicated Version Resolver.

# 20. AP Model Resolution

Once the firmware version has been resolved, the synchronization service derives the AP Model from the Test Run name.

This behavior is implemented using the AP Model Resolver documented in Part I.

```
Test Run

↓

extractApModel()

↓

AP Model
```

Example

```
R750_May4_May8
```

↓

```
R750
```

The AP Model becomes the next level within the repository hierarchy.

---

# 21. Feature Folder Construction

After resolving the firmware version and AP Model, the synchronization service constructs the repository's feature folder.

The feature folder represents the portion of the repository hierarchy that is guaranteed before repository discovery begins.

The constructed hierarchy is

```
Test_Plan/

    Version/

        AP Model/

            Feature/
```

Example

```
Test_Plan/

    V75/

        R750/

            WPA3/
```

At this stage, the synchronization service has not yet determined where the execution run resides.

That decision depends upon repository discovery.

---

## Why Feature Folder Construction Stops Here

The synchronization service intentionally avoids assuming the complete repository structure.

Although the Feature folder is deterministic, the layout beneath it may differ between repositories.

Consequently, synchronization performs repository discovery before constructing the remaining path.

This design allows multiple repository layouts to be supported without modifying synchronization logic.

---

# 22. Repository Discovery

Repository discovery determines how execution data is organized beneath the Feature folder.

Rather than assuming a fixed hierarchy, the synchronization service inspects the repository to determine its layout.

This behavior is implemented by the Repository Discovery Helper.

```
Feature Folder

↓

Repository Discovery

↓

Repository Type
```

The discovered repository type influences every subsequent path resolution step.

---

## Why Repository Discovery Is Necessary

Different projects may organize execution repositories differently.

Instead of forcing every project to adopt a single directory structure, the synchronization service adapts itself by inspecting the repository before continuing.

This significantly improves compatibility across repositories while reducing project-specific configuration.

Repository discovery is therefore an essential step in metadata synchronization.

---

# 23. Run Parent Resolution

Once the repository type has been determined, the synchronization service resolves the parent directory that contains execution runs.

This step is performed by the Run Parent Resolver.

Unlike previous stages, this resolution depends upon both

- the discovered repository type, and
- execution-specific information contained within the synchronization request.

Inputs include

- repository type
- feature folder
- run name
- Case Reference ID
- test case name

The resolver determines where execution runs should be searched.

```
Repository Type

+

Execution Details

↓

Run Parent
```

Separating this responsibility from repository discovery keeps the synchronization workflow modular while supporting multiple repository layouts.

---

# 24. Run Discovery

After identifying the parent directory, the synchronization service locates the execution run itself.

This responsibility belongs to the Run Discovery Helper.

```
Run Parent

↓

Run Discovery

↓

Run Directory
```

Rather than assuming that the requested run already exists at a predetermined location, the synchronization service actively discovers the directory before proceeding.

Once discovered, the run directory becomes the final repository location before the metadata file.

---

# 25. Metadata Path Resolution

With the run directory successfully resolved, the synchronization service constructs the path to the target metadata file.

The metadata filename is constant across every repository.

```
metadata.json
```

The default metadata path therefore becomes

```
Run Directory

+

metadata.json
```

Example

```
Test_Plan/

    V75/

        R750/

            WPA3/

                Run_001/

                    metadata.json
```

This path represents the file that will be downloaded, validated, merged and written during synchronization.

---

# 26. Custom Metadata Path Override

Although metadata paths are normally resolved automatically, the synchronization service also supports an optional override.

If the synchronization request includes

```
custom_minio_path
```

automatic repository resolution is bypassed.

Instead, the supplied path becomes the metadata location.

If the supplied path already ends with

```
metadata.json
```

it is used directly.

Otherwise the synchronization service automatically appends

```
metadata.json
```

to the supplied directory.

Examples

Input

```
Test_Plan/V75/R750/WPA3/Run_001
```

↓

Resolved Path

```
Test_Plan/V75/R750/WPA3/Run_001/metadata.json
```

Input

```
Test_Plan/V75/R750/WPA3/Run_001/metadata.json
```

↓

Resolved Path

```
Test_Plan/V75/R750/WPA3/Run_001/metadata.json
```

This feature is primarily intended for advanced synchronization scenarios where repository discovery is unnecessary or an explicit metadata location is required.

---

# 27. Preparation Output

If every preparation step completes successfully, the Metadata Synchronization Service returns a prepared synchronization context.

This context contains all information required for the merge phase.

Typical preparation data includes

- resolved bucket
- resolved firmware version
- repository type
- metadata path
- normalized Case Reference ID
- existing metadata
- execution metadata

No modifications have yet been made to the repository.

Preparation is responsible only for locating and validating the target metadata before synchronization begins.

# 28. Metadata Reading

Once the synchronization context has been successfully prepared, the Metadata Synchronization Service retrieves the target `metadata.json` file from MinIO.

This responsibility belongs exclusively to the Metadata Service.

Unlike the preparation stage, which determines *where* the metadata file is located, the Metadata Service is responsible only for reading and parsing its contents.

```
Resolved Metadata Path

        │

Read metadata.json

        │

Parse JSON

        │

Return Metadata Object
```

The synchronization workflow intentionally separates metadata discovery from metadata access.

This separation allows repository navigation and storage operations to evolve independently while keeping each component focused on a single responsibility.

---

## Metadata Service Responsibilities

The Metadata Service performs only two operations:

- Reading metadata from MinIO
- Writing metadata back to MinIO

It deliberately avoids performing business logic such as

- duplicate detection
- merge decisions
- repository discovery
- payload validation

These responsibilities belong elsewhere within the synchronization pipeline.

---

# 29. Metadata Validation

After downloading the metadata file, the service validates that its contents represent valid JSON.

This validation occurs immediately after reading the file.

```
Download metadata.json

        │

Parse JSON

        │

Valid?

        │

Yes ─────────► Continue

No ─────────► Synchronization Failed
```

If the metadata file contains malformed JSON, synchronization terminates immediately.

Example

```
Invalid JSON in metadata file:
Test_Plan/V75/R750/WPA3/Run_01/metadata.json
```

Stopping immediately prevents corrupted repository data from being merged or overwritten.

---

## Why Validation Happens Here

The synchronization service assumes that every repository stores metadata in JSON format.

Validating immediately after reading ensures that every subsequent operation works with structured data instead of raw file contents.

---

# 30. Metadata File Not Found

If the requested metadata file cannot be located, synchronization attempts to determine why the lookup failed.

Rather than returning a generic "file not found" error, the service performs path validation.

```
Read metadata.json

        │

Failed?

        │

Locate Invalid Path Segment

        │

Return Detailed Error
```

The synchronization service identifies the first repository segment that could not be resolved.

For example

```
Test_Plan

    V75

        R750

            WPA3

                Regression_Run

                    metadata.json
```

If

```
Regression_Run
```

does not exist, the service identifies this directory as the invalid path segment.

This significantly improves troubleshooting by indicating precisely where repository resolution failed.

---

## Error Code

Metadata lookup failures return

```
FILE_NOT_FOUND
```

along with additional diagnostic information such as

- metadata path
- invalid repository segment
- invalid repository prefix

Providing detailed diagnostics reduces the time required to identify repository configuration issues.

---

# 31. Duplicate Execution Detection

Once the metadata file has been successfully loaded, the synchronization service checks whether the execution already exists.

Duplicate detection is performed before any metadata modifications occur.

```
Metadata Loaded

        │

Duplicate Detection

        │

Duplicate?

        │

No ─────────► Continue

Yes ────────► Check Overwrite
```

This validation prevents multiple execution records from being created for the same test case.

---

## Case Reference ID

Duplicate detection is based on the normalized Case Reference ID.

Before comparison, the synchronization service normalizes the supplied identifier.

```
Incoming Case Reference

        │

Normalization

        │

Normalized Case Reference
```

Normalizing identifiers ensures that logically identical case references are compared consistently regardless of formatting differences.

---

## Repository Awareness

Duplicate detection is repository-aware.

Instead of assuming a fixed metadata structure, the duplicate detector considers the repository type discovered during metadata preparation.

This allows duplicate detection to operate correctly across multiple repository layouts without requiring project-specific implementations.

---

## Duplicate Error

If an existing execution is detected and overwrite has not been requested, synchronization terminates.

Error Code

```
CASE_REF_ALREADY_EXISTS
```

Example

```
Metadata already exists for this Case Ref ID.
```

Returning a dedicated error code allows the Test Case Management platform to distinguish duplicate executions from other synchronization failures.

---

# 32. Overwrite Support

The synchronization service supports explicit overwrite operations.

If the synchronization request specifies

```
overwrite = true
```

duplicate detection still occurs.

However, instead of terminating synchronization, the merge phase replaces the existing execution metadata with the updated information.

```
Duplicate Found

        │

Overwrite?

        │

No ─────────► Error

Yes ────────► Continue Merge
```

This behavior prevents accidental replacement of metadata while still allowing intentional updates.

---

# 33. Building Execution Metadata

Before metadata can be merged, the synchronization service converts the synchronization payload into a standardized execution metadata object.

This responsibility belongs to the Payload Helper.

```
Synchronization Request

        │

Payload Builder

        │

Execution Metadata
```

Separating payload construction from merge logic keeps metadata generation independent of repository operations.

This also ensures that every execution follows a consistent metadata structure regardless of the originating project.

---

# 34. Metadata Merge

After execution metadata has been generated, the synchronization service merges it with the existing metadata.

```
Existing Metadata

+

Execution Metadata

        │

Merge Engine

        │

Merged Metadata
```

The merge operation is performed entirely in memory.

The original metadata file is not modified until the merge completes successfully.

---

## Merge Responsibilities

The Merge Helper determines

- whether an execution should be added
- whether an execution should replace an existing entry
- where execution metadata belongs
- how repository-specific metadata structures are preserved

Separating merge behavior from storage logic allows synchronization rules to evolve without modifying MinIO interactions.

---

## Why Merge Is Isolated

Keeping merge logic independent provides several advantages.

- Easier testing
- Easier maintenance
- Repository independence
- Cleaner synchronization workflow

The Metadata Service remains responsible only for reading and writing files.

Business rules remain inside the Merge Helper.

---

# 35. Writing Metadata

After merging completes successfully, the updated metadata is written back to MinIO.

```
Merged Metadata

        │

Serialize JSON

        │

Upload metadata.json

        │

Synchronization Complete
```

Before upload, the metadata object is converted into formatted JSON.

The synchronization service writes the entire metadata document as a single operation.

---

## Metadata Serialization

Serialization converts the metadata object into a human-readable JSON document.

Indented formatting improves readability for repository maintainers while simplifying future debugging.

If serialization fails, synchronization terminates immediately.

---

## Upload Operation

Writing metadata consists of a single upload operation.

The Metadata Service delegates the actual storage operation to the MinIO client.

This abstraction allows storage implementation details to remain isolated from synchronization logic.

# 36. Synchronization Response

After successfully writing the updated metadata file, the synchronization service returns a success response.

A typical response contains

- synchronization status
- bucket
- metadata path
- updated metadata

Example

```json
{
    "success": true,
    "bucket": "legacyruckus",
    "metadataPath": "Test_Plan/V75/R750/WPA3/Run_01/metadata.json",
    "metadata": { ... }
}
```

Returning the metadata path simplifies debugging while confirming exactly which repository object was updated.

---

# 37. Error Handling Strategy

The Metadata Synchronization Service follows a fail-fast approach.

Whenever an unrecoverable error occurs, synchronization terminates immediately.

Examples include

- invalid request payload
- bucket resolution failure
- version resolution failure
- repository discovery failure
- metadata file not found
- invalid JSON
- duplicate execution (without overwrite)
- metadata serialization failure
- upload failure

Stopping immediately prevents partial synchronization and preserves repository consistency.

---

## Error Philosophy

The synchronization service prefers returning precise, actionable errors instead of generic failure messages.

Where possible, each error includes additional context such as

- metadata path
- repository segment
- Case Reference ID
- synchronization stage

Providing contextual information significantly reduces troubleshooting effort.

# 40. Repository Discovery Helper

## Purpose

The Repository Discovery Helper determines how execution data is organized beneath a Feature directory.

Unlike traditional directory traversal, the helper does **not** recursively inspect the repository.

Instead, it classifies the repository based solely on the immediate child directories contained within the Feature folder.

This classification determines how all subsequent path resolution operates.

---

## Responsibilities

The Repository Discovery Helper is responsible for

- Listing immediate directories beneath the Feature folder
- Ignoring nested directories
- Ignoring files
- Identifying repository structure
- Returning repository metadata

The helper never

- reads metadata.json
- modifies repository contents
- creates folders
- performs synchronization

Its responsibility ends once the repository type has been identified.

---

## Repository Discovery Workflow

```
Feature Folder

        │

List Immediate Objects

        │

Filter Directories

        │

Extract Child Directory Names

        │

Classify Repository

        │

Return Repository Information
```

---

## Immediate Directory Extraction

Repository discovery intentionally examines **only one level** beneath the Feature folder.

For example

```
Feature/

    Run001/

    Run002/

    Run003/
```

The helper returns

```
Run001

Run002

Run003
```

Nested directories are deliberately ignored.

Example

```
Feature/

    Run001/

        Logs/

        Results/

        metadata.json
```

Only

```
Run001
```

is considered during repository discovery.

This behaviour keeps repository classification deterministic while avoiding unnecessary object listings.

---

## Why Non-Recursive Discovery?

Recursive directory traversal introduces several disadvantages.

- Higher MinIO API usage
- Increased synchronization latency
- Unnecessary processing
- Greater implementation complexity

Since repository type can be determined from the immediate child directories, recursive traversal provides no additional value.

The Metadata Synchronization Service therefore performs only non-recursive listings.

---

# 41. Repository Classification

After extracting the immediate directories, the Repository Discovery Helper determines the repository type.

Classification is pattern-based.

The helper examines directory names and compares them against predefined repository conventions.

---

## FEATURE Repository

A repository is classified as a FEATURE repository if immediate child directories match the Run naming convention.

Example

```
Feature/

    Run001/

    Run002/

    Run003/
```

Classification Result

```
FEATURE
```

Execution metadata for FEATURE repositories is stored collectively.

Multiple executions share a single metadata file.

---

## TESTCASE Repository

A repository is classified as a TESTCASE repository if immediate child directories match testcase identifiers.

Example

```
Feature/

    TC_1001/

    TC_1002/

    TC_1003/
```

Classification Result

```
TESTCASE
```

Each testcase directory owns its own execution metadata.

---

## UNKNOWN Repository

If neither naming convention is detected, the helper classifies the repository as

```
UNKNOWN
```

This prevents synchronization from making incorrect assumptions regarding repository layout.

Synchronization subsequently terminates with an appropriate error.

---

## Repository Discovery Output

Successful repository discovery returns structured information describing the repository.

The result includes

- repository type
- discovered directories
- run directories
- testcase directories

This information becomes the input for the Run Parent Resolver.

Repository Discovery therefore acts as the foundation for all subsequent repository navigation.

---

# 42. Supported Repository Layouts

The Metadata Synchronization Service currently supports two repository organizations.

---

## Layout 1 — FEATURE Repository

```

    V75/

        R750/

            WPA3/

                Run001/

                    metadata.json

                Run002/

                    metadata.json
```

Characteristics

## Layout 2 — TESTCASE Repository

# 43. Design Decisions

Repository Discovery intentionally follows several architectural principles.

### Discovery Before Assumption

The synchronization service never assumes repository organization.

Instead, it discovers the repository structure before continuing.

---

### Convention Over Configuration

Repository classification relies on directory naming conventions rather than project-specific configuration files.

This simplifies deployment while reducing maintenance effort.

---

### Read-Only Behaviour

Repository Discovery never modifies repository contents.

Its responsibilities are limited to observation and classification.

This guarantees that repository inspection cannot accidentally alter project data.

---

### Separation of Concerns

Repository Discovery determines **what** the repository looks like.

It does **not** determine

- where runs are stored
- where metadata exists
- how metadata should be merged

Those responsibilities belong to later components within the synchronization pipeline.

# 44. Run Parent Resolver

## Purpose

After the repository structure has been identified, the Metadata Synchronization Service must determine where execution runs are expected to exist.

Although the Feature directory has already been resolved, the service cannot yet search for the requested Run directory because different repository types organize execution data differently.

This responsibility belongs exclusively to the **Run Parent Resolver**.

Rather than locating the Run itself, the resolver identifies the directory that should contain the Run.

```
Repository Discovery

        │

Determine Repository Type

        │

Resolve Run Parent

        │

Return Parent Directory
```

The resulting parent directory becomes the starting point for Run Discovery.

---

## Responsibilities

The Run Parent Resolver is responsible for

- determining the correct Run parent directory
- supporting multiple repository layouts
- validating required repository information
- providing compatibility for legacy testcase repositories

The resolver deliberately avoids

- listing directories
- reading metadata
- locating Run folders
- modifying repository contents

These responsibilities belong to other components.

Repository structure

```

    Run001/

    Run002/

    Run003/
```

Because no testcase layer exists, the Feature directory itself becomes the Run parent.

```

        │

Run Parent

↓

Feature Folder

```

```

    V75/

        R750/

            WPA3/
```

No additional path resolution is required.

## Validation

Example

```
Run002

Run003
```


Result


This validation prevents unnecessary MinIO operations later in the synchronization workflow.

# 50. Path Resolution Strategy

One of the defining characteristics of the Metadata Synchronization Service is that repository paths are **discovered**, not constructed.

Many synchronization services concatenate directory names and assume the resulting path exists.

For example

```

+

+

Feature

+
```

↓

```

```

The Metadata Synchronization Service deliberately avoids this approach.

```

        │

        │

        │

Resolve metadata.json
```

Every stage confirms that the repository structure actually exists before constructing the next path.

This significantly improves robustness while producing more informative error messages.

Rather than attempting to continue after encountering an invalid repository structure,

Validation occurs incrementally.

```
Version

✓

Repository

✓

Run Parent

✓

Run

✓

Metadata
```

Each stage depends upon the successful completion of the previous stage.

This layered validation simplifies debugging because synchronization failures occur at the earliest possible point.

# 53. Metadata Service

## Purpose

The Metadata Service is the storage abstraction layer of the Metadata Synchronization Service.

Its sole responsibility is to interact with MinIO by reading and writing `metadata.json` files.

Unlike the Synchronization Service, the Metadata Service contains **no business logic**.

It does not

- resolve repository paths
- determine repository types
- detect duplicate executions
- merge metadata
- validate synchronization requests

Instead, it exposes a simple interface for persistent storage operations.

```
Synchronization Service

        │

Read Metadata

        │

Metadata Service

        │

MinIO

        │

metadata.json
```

---

## Responsibilities

The Metadata Service performs only two operations.

| Function | Responsibility |
|----------|----------------|
| readMetadata() | Downloads and parses metadata.json |
| writeMetadata() | Serializes and uploads metadata.json |

This strict separation keeps storage logic independent from synchronization logic.

---

# 54. Reading Metadata

The synchronization workflow begins by retrieving the existing metadata file from MinIO.

The Metadata Service validates the request before attempting any storage operation.

Validation includes

- Bucket name exists
- Object key exists

Once validated, the service downloads the file from MinIO.

```
Bucket

        │

Object Key

        │

Download

        │

metadata.json

        │

Parse JSON

        │

Return Metadata Object
```

---

## JSON Parsing

The downloaded metadata is expected to be valid JSON.

The Metadata Service parses the document before returning it.

```
metadata.json

        │

JSON.parse()

        │

Metadata Object
```

If parsing fails,

synchronization immediately terminates.

Example

```
Invalid JSON in metadata file:

metadata.json
```

This prevents malformed metadata from propagating through the synchronization pipeline.

---

# 55. Writing Metadata

After synchronization completes,

the Metadata Service uploads the updated metadata back into MinIO.

Before upload,

the metadata object is validated.

The service verifies

- Bucket exists
- Object key exists
- Metadata is an object
- Metadata is not an array

Only after validation succeeds is serialization performed.

```
Metadata Object

        │

Validation

        │

Serialize JSON

        │

Upload

        │

Success
```

Advantages include

- Human readability
- Easier debugging
- Cleaner repository history
- Simpler manual inspection

If serialization fails,

synchronization immediately stops.

- what should be preserved

This separation makes the service reusable for future synchronization workflows.

# 71. Error Handling Strategy

The Metadata Synchronization Service follows a fail-fast architecture.

Whenever a synchronization stage encounters an unrecoverable error,

execution stops immediately.

No further repository operations are performed.

```
Synchronization Stage

        │

Error?

        │

Yes

↓

Return Error
```

This prevents partial repository updates and maintains metadata consistency.

# Appendix A – REST API Specification

## Overview

The Metadata Synchronization Service exposes a REST API that allows the Test Case Management (TCM) platform to synchronize execution metadata with the MinIO repository.

The API accepts execution information, validates the request, discovers the appropriate repository structure, updates the metadata, and returns the synchronization result.

---

## Endpoint

| Property | Value |
|----------|-------|
| Method | POST |
| Endpoint | /sync |
| Content-Type | application/json |

---

## Request Body

| Field | Type | Required | Description |
|---------|------|----------|-------------|
| project | String | ✓ | Project used for bucket resolution |
| testRun | String | ✓ | Test run name used for AP model extraction |
| feature | String | ✓ | Feature directory name |
| run | String | ✓ | Run directory |
| case_ref_id | String | ✓ | Unique testcase reference identifier |
| status | String | ✓ | Execution status |
| executedBy | String | ✓ | User who executed the testcase |
| executedAt | String | ✓ | Execution timestamp |
| overwrite | Boolean | No | Allows replacement of existing execution metadata |
| custom_minio_path | String | No | Overrides automatic metadata path discovery |

---

## Example Request

```json
{
    "project": "LegacyRuckus",
    "testRun": "R750_Regression",
    "feature": "WPA3",
    "run": "Run001",
    "case_ref_id": "TC_1001",
    "status": "PASS",
    "executedBy": "Automation",
    "executedAt": "2026-07-21T10:30:00Z",
    "overwrite": false
}
```

---

## Successful Response

```json
{
    "success": true,
    "bucket": "legacyruckus",
    "metadataPath": "Test_Plan/V75/R750/WPA3/Run001/metadata.json",
    "metadata": {
        ...
    }
}
```

---

## Example Error Response

```json
{
    "success": false,
    "message": "CASE_REF_ALREADY_EXISTS"
}
```

---

## HTTP Status Codes

| Status | Description |
|---------|-------------|
| 200 | Synchronization successful |
| 400 | Invalid request |
| 404 | Repository or metadata not found |
| 409 | Duplicate execution detected |
| 500 | Internal server error |
